## Renderer findings

The new zoom pack should use the existing `type: image`, `effect: zoom` renderer. This path applies each question's `origin` as `transform-origin`. It displays the crop at 3.4× for 200/400 points and 3.16× for 600/800/1000 points, where the current assistance feature applies. Revealing the answer changes the scale to 1 and enables the lightbox. Hiding the answer passes the hidden state back to the media renderer, restoring the crop and disabling lightbox access.

The older `type: zoom` image branch does **not** apply `question.origin`; only its emoji branch does. The existing pack uses the generic image/effect path, so this legacy branch is not a reason to change the current renderer. These findings come from source inspection and are not a substitute for runtime interaction tests.

## Final 40-card static crop review

After the final zoom pack was integrated, decoded all 40 referenced files and generated five contact sheets, one per tier. Each sheet pairs the full image with a marked crop boundary and the resulting crop. Reviewed every pair. All files are 1280×960, totaling **4,681,606 bytes (4.46 MiB)**. All 40 crop boundaries remain within their source images; none exposes a blank area in place of the intended object, and no wrong-object crop was found. **No question or origin was changed by this review.**

The inverse transform for source dimensions `W × H`, normalized origin `(ox, oy)`, and CSS scale `s` is:

- `left = ox × W × (1 − 1/s)`; `top = oy × H × (1 − 1/s)`.
- `cropWidth = W/s`; `cropHeight = H/s`.
- Used `s = 3.4` for 200/400 and `s = 3.16` for 600/800/1000. Sharp extraction rounds to the nearest source pixel.

The crop center is consequently not identical to the configured transform origin. These calculations model the image element's clipping stage for the 4:3 assets at portrait phone widths, where the image is below the 46vh height cap. They do not prove actual browser layout dimensions or desktop behavior when that cap applies.
