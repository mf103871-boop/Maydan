# نشر ميدان الإنتاجي المراجع

أوامر `npm run cloudflare:deploy` و`npm run rooms:deploy` ترفض النشر دائمًا. لا يوجد متغير بيئة أو `--force` لتجاوزهما. `cloudflare:build-only` يعيد تقريرًا يؤكد أن البناء وحده لا ينشر شيئًا.

Cloudflare Builds يبني `main` كالمعتاد. أمر النشر المقترح له عبارة Node ثابتة تطبع أن النشر يحتاج مراجعة، وتنجح دون استدعاء ملف من المستودع أو Wrangler أو أي عملية شبكة. تعمل أيضًا على الإصدارات الأقدم التي لا تحتوي ملفات الحماية الجديدة. لم تعد هناك قائمة SHAs يؤدي الخروج عنها إلى نشر تلقائي. هذا يمنع النشر العرضي في مرحلة deploy المهيأة؛ ليس عزلًا أمنيًا ضد شخص يغيّر build command أو يضع كودًا خبيثًا في عملية البناء نفسها.

## ما الذي يُراجع قبل نشر الإنتاج؟

1. تُجمّد نسخة المصدر وتُراجع SHA وملفات الخادم وتبعياته. يجب أن يكون checkout كاملًا نظيفًا؛ التعديلات المحلية الحالية ليست إصدارًا إنتاجيًا معتمدًا.
2. تؤخذ قراءات جديدة لكل من `maydan-game` و`maydan-rooms`: الإصدار الفعّال، آخر إصدار مرفوع، الإعدادات والربط والأسرار بأسمائها فقط والموارد وDO migration tags والمواعيد. يجب أن يكون آخر إصدار مرفوع هو الإصدار الفعّال بنسبة 100%، ويُعاد فحص ذلك مباشرة قبل كل كتابة.
3. يُستخدم `privateBankManifest` و`bundlePreservedMafiaWorker` من `scripts/mafia-preserved-bundle.mjs`. تبقى مصادر ارسمها الخاصة خارج المستودع العام، وتدخل حزم الخادم في الذاكرة فقط، ثم تُحفظ مشفّرة. تُثبت مطابقتها للإنتاج الحالي، لا لنسخة البنك العامة المحدودة.
4. تُثبت صفحة الدعم وGET/HEAD ورؤوسها، وأصول اللعبة والاستوديو وصلاحياته الخاصة، وسلوك سياسة التحديث في الدول الأربع. تُورث جميع الإعدادات الحية؛ إعدادات المستودع القديمة، ومنها Paddle sandbox، ليست بديلًا عن الإعدادات الحية.
5. يُنتج `pairedPreservationDraft` مسودة بالخادمين. تُراجع بصمات الحزم نفسها التي اختُبرت، ومخطط/ترحيلات D1 الإضافية المطلوبة، ونسخة احتياطية مشفّرة حديثة. لا يُغيّر مخطط قاعدة البيانات ضمن تحديث إعدادات الأداء.
6. تُجمع أدلة المزود الحقيقي والسرية والتوافق. تفعيل مافيا للعامة يحتاج أدلة الأجهزة البشرية والتوازن المقررة؛ نجاح unit tests أو المحاكيات لا يعوضها. حارس مافيا الحالي يسمح بمسار الترحيل الذي راجعه صراحةً فقط، ولا يُوسّع تلقائيًا لترحيلات A–G الأحدث.
7. يُخزّن مستند المراجعة `paired-release-review.dpapi` في مجلد خاص خارج المستودع، ويحتوي `schemaVersion:1` و`kind:production-paired-review` و`snapshots/currentSnapshots` و`before/after/evidence/draft` و`recheckedAt`. دليل المصدر يحتوي `sourceCommit` و`backendTreeSha256`. يُراجع بالبصمة المحددة:

   ```text
   npm run cloudflare:release:review -- <private-directory> <reviewed-document-sha256>
   ```

   الأداة تقرأ الدليل فقط وتستخدم `assertMafiaReleasePreservation` و`preservedMafiaUploadMetadata` و`assertLease` الموجودة. حتى عند النجاح تظل `applyAvailable:false` و`readyToApply:false`؛ لا يوجد أمر رفع أو تفعيل فيها.
8. التنفيذ الفعلي يحتاج عاملًا خاصًا جديدًا، مثبت المصدر والبصمة، يُراجع مستقلًا ويستخدم وراثة الربط الصارمة و`keep_assets`، مع سجل نية دائم وحصري قبل كل كتابة. يبدأ بالخادم game ثم rooms بسبب الربط المشترك. لا يُستخدم `wrangler deploy` العام ولا أي عامل تاريخي مغلق كبديل.

نشر الخادمين ليس معاملة ذرية من Cloudflare؛ يجب أن يظل البروتوكول متوافقًا أثناء الانتقال وأن تتوقف العملية عند أي اختلاف. النتيجة المجهولة تُصالح بقراءات فقط؛ لا تُعاد الكتابة ولا يُحذف القفل. تفعيل ميزات جديدة مستقل عن نشر كود متوافق ومعطّل افتراضيًا.

## تجربة إعدادات الأداء في المعاينة

`scripts/cloudflare-settings-plan.mjs` يولد وثائق مراجعة نقية ولا يملك شبكة أو بيانات اعتماد. يرفض عمال الإنتاج أو DB/R2/DO غير المعاينة، أو إصدارات active/latest المختلفة، أو الدليل القديم أو قيم الأسرار. يطلب دليل كود وأصول ومواعيد، ونقاط تحقق حديثة بأن الغرف/الحجوزات/المكالمات/المشاركين النشطين تساوي صفرًا.

التغيير المهيأ في `wrangler.mafia-preview.jsonc` هو Smart Placement، وتنقيح query strings، وتتبّع بنسبة 5%. تظل إعدادات logs و`invocation_logs:false` كما هي؛ لذلك لا نعدّ السجلات عينة مكتملة لكل طلب HTTP. لا يتغير CPU limit أو خطة مدفوعة أو cron أو بيانات أو نظام الصوت أو البروتوكولات. هذه إعدادات مصدر محلية، وليست دليلًا على تطبيقها حيًا.

هناك واجهتان مختلفتان في Cloudflare:

- `PATCH /workers/scripts/<name>/script-settings` يقبل JSON لإعدادات مستوى العامل، ومنها observability، دون رفع كود. هذا هو المسار الأضيق لتجربة الرصد وحدها.
- `PATCH /workers/scripts/<name>/settings` يستخدم multipart باسم **settings** لتغيير إعدادات الإصدار، ومنها placement. تغيير الإعدادات ينشئ إصدارًا؛ لا نفترض أن تغيير active/latest غير مهم. المسودة المركبة تورث جميع أسماء الربط بـ`type:inherit,version_id:latest`، وتحافظ على خصائص التشغيل والوسوم القابلة للكتابة؛ `workers/triggered_by` يملكه الخادم. لا تُرسل migrations أو export-reconciliation.

إذا قُسمت التجربة إلى المرحلتين، تؤخذ مسودة وبصمة جديدة بعد نجاح الأولى؛ لا يُعاد استخدام بصمة baseline قديمة. `inherit` في هذا المسار يرجع إلى آخر إصدار مرفوع؛ لذلك يشترط التحقق المباشر من active/latest، ولا تُستخدم UUID ثابتة في version_id لأن هذا المسار يقبل `latest` فقط.

المسار المعتمد أولًا هو `previewObservabilityPlan`: يرسل JSON يتضمن observability فقط إلى `script-settings`، ويشترط بقاء active/latest كما هما. يستخدم `assertPreviewPlanLease` للفحص السابق و`assertPreviewObservabilityResult` للفحص اللاحق. Smart Placement يبقى لرفع المعاينة الجديد المراجع أو خطة مستقلة جديدة؛ المسودة المركبة ليست تصريحًا لتجاوز المرحلتين. إضافة متغيرات metrics ليست جزءًا من PATCH الرصد.

المراجع يحفظ نية واحدة، ويعيد فحص البصمة وعدادات الخلو، ثم يقارن بعد التغيير الكود/ETag والأصول والربط والقيم والمواعيد وإعدادات التشغيل والإنتاج كله. لا يُرفع الإصدار المحلي غير المعتمد بسبب تجربة إعدادات. إذا تغيّر ETag أو ظهرت نسخة غير مفعّلة، تتوقف العملية للمصالحة ولا يحدث تفعيل أو إعادة PATCH تلقائيًا.

نقاط الخلو تعكس عقود/بيانات D1 التي فُحصت، وليست قفل قبول ذريًا أو ضمانًا بأن لاعبًا لن يدخل لاحقًا. يجب توثيق حدود تغطية الغرف الخاصة وأي نشاط بين الفحص والكتابة؛ لا نوقف دخول اللاعبين أو ننهي مبارياتهم لتسهيل التجربة.

## الرجوع والتحقق

وثيقة تغيير Build trigger تحتوي فرق الحقل `deploy_command` فقط وبصمات before/after/request. الرجوع إلى الأمر القديم يعيد خطر النشر التلقائي، لذلك ليس خيارًا تلقائيًا؛ يبقى أمر البناء فقط هو الحالة الآمنة عند التعثر.

وثيقة إعدادات المعاينة تتضمن placement/observability السابقين. الرجوع يحتاج قراءة after جديدة وعدادات خلو حديثة وسجلًا جديدًا، ويورث الربط من الإصدار الحالي بعد التأكد من مطابقته. لا تعاد كتابة لقطة قديمة بكاملها، ولا تستخدم rollback للتعامل مع نتيجة طلب مجهولة قبل المصالحة.

التحقق يقارن زمن المسارات الفعلية وCPU وI/O وACK قبل وبعد، بعينة متشابهة وشبكة معلومة. Smart Placement لا ينقل Durable Objects أو D1، ولا يضمن تحسن الصوت أو الشبكات الضعيفة. الأصول التي تقدم مباشرة تظل قرب المستخدم، أما ما يمر عبر `ASSETS.fetch` فيتأثر بمكان العامل. لا تُرفع الحدود أو تُحذف المهام المجدولة ضمن هذه التجربة.

المراجع الرسمية التي تم التحقق منها: [Script and version settings](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/script_and_version_settings/)، [Versions and deployments](https://developers.cloudflare.com/workers/versions-and-deployments/)، [Placement](https://developers.cloudflare.com/workers/configuration/placement/)، [Tracing](https://developers.cloudflare.com/workers/observability/traces/)، ومخطط Wrangler المثبت `4.149.0`.
